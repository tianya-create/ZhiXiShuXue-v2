# RAG 受控评测框架设计

> 目标：把知识追踪项目里那套「受控对照 + 分组防泄漏 + 冻结配置 + 独立审计」的评估纪律，
> 移植到 RAG 上，用来回答一个比"我的 RAG 效果如何"更硬的问题：
>
> **检索这一环到底贡献了多少，且这个贡献不能由"上下文变长"或"模型本来就会"解释。**

---

## 0. 为什么不能直接跑 benchmark 报个数

常规 RAG 评测只有一个数字：RAG vs 不作为基线的准确率。这个数字有三个无法排除的竞争解释：

| 竞争解释 | 常规评测能否排除 | 本框架的排除手段 |
|---|---|---|
| 增益来自**上下文变长 / prompt 变复杂**，而非检索内容相关 | 否 | 随机检索臂 X（等 token 预算、等块数、无关内容） |
| 增益来自**模型参数里本来就有**这个知识 | 否 | 无检索臂 N 就是参数记忆的度量；再加语料/时间切分 |
| 增益来自**评测集被见过**（prompt 调参、few-shot 取自评测集、答案在索引里） | 否 | 双轴分组 + 哈希断言（见 §4） |

所以本框架不是为了得到更高的数字，是为了让"没有增益"这个结论也站得住——反过来，
只有能证明"没有增益"的框架，它报出来的"有增益"才可信。

---

## 1. 从 KT 继承的四条原则

| 原则 | KT 里的形态 | RAG 里的形态 |
|---|---|---|
| **先算覆盖率，再谈增益** | 图覆盖率 17.9% → 直接判定不值得做图对照 | 答案在语料里的比例 + oracle 召回率 → 决定要不要跑三臂 |
| **同预算对照** | 五组模型参数量/训练轮数对齐 | 三臂 token 预算、块数、prompt 模板逐字一致 |
| **未舍入 CI 判向** | `ciPreciseOf`：4 位舍入会把 [0.00004,…] 变成 [0,…] | 同一函数直接复用；覆盖率/准确率差异常在小数第 3 位 |
| **结论可独立复算** | 审计器不重训，只从落盘预测复算 164 项 | 审计器不重跑生成，只从落盘 log + judge 记录复算 |

关键差别：**KT 是确定性训练（固定种子即完全复现），RAG 不是。** 生成有采样随机性，
judge 是"有噪声的尺子"。所以下面 §3 和 §6 是必须新增的，不能照搬。

## 2. 实验臂结构（三核心 + 一诊断）

### 2.1 三个核心臂

| 臂 | 输入 | 控制住的变量 | 回答什么 |
|---|---|---|---|
| **N**（no-retrieval） | query only | 参数记忆下界 | 模型不听上下文时能做到多少 |
| **X**（random-retrieval） | query + 与 R 臂**等 token 数**的随机块 | 上下文长度、块数、prompt 形态 | "有上下文"本身值多少 |
| **R**（retrieval） | query + top-k 检索块 | 待测变量 | 端到端效果 |

**ΔRET = R − N**：检索（含长度）的总增益。
**ΔREL = R − X**：**检索内容相关性**的净增益 ← 这才是要报的主效应。

如果 ΔRET 显著但 ΔREL ≈ 0，说明增益全部来自"多给了上下文"，
换更好的 retriever 不会有任何改善——这是一个非常常见但常规评测看不出来的结论。

### 2.2 等长随机的实现要求（X 臂最容易做错）

X 臂若简单地"随机取 top-k 块"，会有三个漏洞，必须逐个堵：

1. **长度不匹配** → X 的上下文比 R 短，测的就不是"相关性"而是"长度"。
   做法：对每个 query q，先取 R 臂实际检索到的 token 数 `T_q`，再从全语料按
   `seed = hash(configSeed, qid)` 打乱后贪心累积采样，截断到 `|T_x − T_q| / T_q ≤ 2%`。
2. **块间重叠/同源** → 随机块可能有近重复，等价于给了更多有效信息。
   做法：随机块取自 **doc 簇**（§4.2）而非单篇，且簇间不重复。
3. **拒答倾向不同** → R 臂上下文相关、X 臂上下文无关，模型在 X 下更容易说
   "资料中没有提到"。若 system prompt 不同，这会变成 prompt 差异而非相关性差异。
   做法：**三臂使用逐字相同的 prompt 模板**，仅 `{context}` 槽位内容不同；
   N 臂该槽位为空字符串而非删除整段（保留模板结构）。

### 2.3 第四个诊断臂 O（可选，不影响三臂结论）

| 臂 | 输入 | 用途 |
|---|---|---|
| **O**（oracle） | query + 人工标注的 gold 块 | 生成器的能力上限 |

用途是把失败定位到具体环节，形成 2×2：

| | O >> N | O ≈ N |
|---|---|---|
| **R >> X** | 检索与生成都正常，RAG 成立 | 检索到了但模型不用 → 修 prompt/生成器 |
| **R ≈ X** | **检索器是瓶颈** → 换 embedding/reranker 有意义 | **任务不需要 RAG** → 换任务或换语料 |

没有 O 臂就只能说"效果不好"，无法说"不好在哪"——这对工程决策是致命的。
O 臂成本只是一次额外生成，建议默认带上；若语料没有 gold 标注，用「BM25 top-3 + 人工过一遍」
构造一个 50 条的 oracle 子集即可。

## 3. 指标分层：把噪声大的指标放对位置

RAG 评测的指标可靠性差异极大，混在一起报会互相污染。

| 层 | 指标 | 噪声来源 | 在本框架中的角色 |
|---|---|---|---|
| **L1 检索层** | recall@k、nDCG@k、MRR | 无（确定性计算） | **上限诊断**，零成本，先跑 |
| **L2 生成层** | EM、token-F1、citation precision | 仅生成采样 | **主指标**（可复算、可审计） |
| **L3 判定层** | LLM-judge 0–2 分、faithfulness | 采样 + judge 偏差 + judge 版本 | **稳健性复核**，不做唯一主指标 |

三条硬规矩：

1. **主指标必须在配置里预注册**，写完不许换。L2 与 L3 结论冲突时，以 L2 为准并如实报告冲突。
2. **L3 必须做人工校准**：抽 10%（不少于 50 条）双人标注，报 judge-human 准确率与 Cohen's κ。
   κ < 0.6 时 L3 只能作参考，不得作为判定依据。
3. **judge 模型版本进哈希**。换 judge = 换尺子，必须重算历史结果并在配置里留痕
   （对应 KT 的 `statisticsRevision`）。

## 4. 分组防泄漏（双轴）

KT 里防泄漏的单位是「学生」——同一学生的多条记录不能跨折，否则同一个人既在训练又在测试。
RAG 有两个同构但独立的泄漏轴，**两个都要切**。

### 4.1 轴一：query 簇（防"同一问题的不同问法"）

同一事实的多种问法（同义改写、换语言、加限定词）在语义上几乎等价。
若问法 A 在 dev、问法 B 在 eval，调 prompt 时等于偷看了 eval。

做法：
1. 用 embedding 相似度聚类 query，阈值 **冻结在配置里**（例如 cosine ≥ 0.92 连边，连通分量成簇）。
2. 以**簇 id** 为分组单位分配 dev/eval，不是以 query 为单​​位。
3. 审计断言：`set(dev_cluster_ids) ∩ set(eval_cluster_ids) = ∅`。

这就是 KT 里 `groupKFold(userIds, …)` 的直接对应，只是 key 从 `userId` 换成 `queryClusterId`。

### 4.2 轴二：doc 簇（防"答案所在文档两边都有"）

语料里同一段内容的多个副本（PDF 重排版、网页转载、FAQ 模板）会互相"作弊"：
eval 查询的答案文档若在 dev 里出现过，模型可能在调 prompt 阶段就学到了它的表述。

做法：
1. MinHash（shingle=5）+ Jaccard ≥ 0.8 聚类，阈值冻结。
2. 以 **doc 簇 id** 为分组单位。
3. 若评测需要 k-fold 调参（如 reranker 阈值），用 `groupKFold(docClusterIds)`，
   保证同簇不跨 fit/validate 折。

### 4.3 另外三条必须断言的泄漏

| 泄漏 | 断言 |
|---|---|
| few-shot 示例取自 eval 查询 | 示例 query id 与 eval query id 无交集，且与 eval 的 query 簇无交集 |
| 索引里含评测查询本身（自检索） | 建索引的文档集与"eval 查询来源集"分离；若同源，报告自命中率 |
| 看着 eval 结果改 prompt | eval 结果哈希在首次运行后冻结；任何 prompt 改动必须新增 `revision` 记录并触发全量重跑 |

## 5. 冻结配置（两阶段）

### 5.1 为什么必须两阶段

KT 里的阈值是「2σ」推出来的（ΔAUC std 0.001047 → 阈值 0.002）。
RAG 的噪声底**无法先验知道**，且比 KT 大一到两个数量级。所以：

```
Stage 0  预检（只用 dev 集，eval 集一次都不碰）
   ├─ 语料覆盖率审计        → 决定值不值得跑三臂
   ├─ 噪声底 pilot          → 同一臂、不同生成种子，跑 3 遍，得到 Δ 的 σ
   └─ judge 校准（50 条）   → κ 不达标就先修 rubric
         ↓
Stage 1  冻结 config（阈值由 Stage 0 的 σ 推出：阈值 = 2σ 或 3σ，写进 JSON）
         ↓
Stage 2  三臂（+O）全量运行，eval 集首次解封
         ↓
Stage 3  独立审计（不重跑生成）
         ↓
Stage 4  判定 + 决策
```

**反作弊要点**：Stage 0 结束后，`config` 的 sha256 与 eval 集 sha256 一起写入
`freeze-manifest.json`；后续任何运行的审计器第一件事就是比对这两个哈希。

### 5.2 语料覆盖率预检（决定要不要做的闸门）

三个口径，全部在评估任何模型之前算：

| 口径 | 定义 | 作用 |
|---|---|---|
| `answer_in_corpus_rate` | gold 答案（或其关键实体/n-gram）是否出现在语料任一块 | 语料缺内容的比例 |
| `oracle_recall@k` | 用 gold doc 直接当检索结果，top-k 能否覆盖 | 分块策略的损失 |
| `generator_ceiling` | O 臂在 gold context 下的准确率 | **效果天花板** |

判定：

- `answer_in_corpus_rate < 0.6` → **先补语料，不要调模型**。这是最常见也最致命的坑。
- `generator_ceiling − N 臂 ≈ 0` → 模型不用上下文，RAG 在这套 prompt 下不可能有效。
- `oracle_recall@k` 明显低于 1 → 分块策略有问题（块太小/切断了答案），先修 chunking。

这一条完全对应 KT 里「图覆盖率 17.9% → 直接 stop」——
只是 RAG 的覆盖率通常可修（补语料），而图覆盖率不可修（数据本身没有边）。

## 6. 功效预算（这一节决定框架是否可信）

### 6.1 一个反直觉但关键的事实

bootstrap 的重采样单位是 **query**，不是 **生成样本**。
所以「每个 query 生成 5 次取平均」**不能收窄置信区间**——它只降低单个 query 的
分数噪声，不增加独立信息量。CI 宽度只由 query 数决定：

```
SE(Δ) ≈ sqrt(p_discordant / n_queries)
```

其中 `p_discordant` 是两臂答案不一致的 query 比例（配对设计下只有不一致的对子贡献方差）。

### 6.2 可检出最小效应（MDE，α=0.05 双侧，power=0.8）

| n_queries | p_disc = 0.10 | p_disc = 0.20 |
|---|---|---|
| 200 | 6.3 pp | 8.9 pp |
| 500 | 4.0 pp | 5.6 pp |
| 1000 | 2.8 pp | 4.0 pp |
| 2000 | 2.0 pp | 2.8 pp |

**结论：**
- 评测集 200 条时，只有 ≥9pp 的增益才可能被判为显著。RAG 论文里常见的 +2~3pp
  在 200 条上**统计上不可检出**，报出来的是噪声。
- 要可靠检出 3pp 级差异，需要 **1000–1500 条** query，且两臂高度相关（p_disc 低）。
- 这就是 KT 那堂课的同构版本：效应 1e-4、噪声 5e-3，五个种子只能给"不确定"。
  **样本量不够时，正确的结论是"不确定"，不是"有效"或"无效"。**

### 6.3 成本估算

```
生成次数 = n_queries × arms × samples_per_query
token 量 ≈ 生成次数 × (avg_prompt_tokens + avg_completion_tokens)
```

例：500 query × 4 臂 × 3 samples = 6,000 次生成；按 1.5k 输入 / 200 输出估算
≈ 9.0M 输入 + 1.2M 输出 token。用小模型做主体、大模型只做 L3 判定的抽检，
这个规模完全在可承受范围内——**成本不是瓶颈，样本量和语料质量才是。**

## 7. 独立审计器（不重跑生成）

沿用 KT 审计器的定位：**它是"检查者"不是"执行者"**，只读落盘产物。

| # | 检查类别 | 具体断言 | 对应 KT 检查 |
|---|---|---|---|
| 1 | 产物哈希 | 语料/分块清单/索引/eval 集/judge prompt 的 sha256 与 config 一致 | `inputs.resultsSha256` 绑定 |
| 2 | 预算等长 | 每 query 三臂的 prompt token 数差 ≤ 2%；块数相等 | 参数量/轮数对齐 |
| 3 | X 臂真实性 | X 的 doc 簇 id 与 R 的**无交集**；token 长度分布 KS 检验 p > 0.05 | 随机图护栏 ΔC |
| 4 | 泄漏断言 | dev∩eval 的 query 簇、doc 簇均为空；示例 query 不在 eval | 学生级分组 |
| 5 | 指标可复算 | 从原始 log 重算 L1/L2，与 summary 逐位一致（未舍入），否则拒绝 | P2 精度纪律 |
| 6 | judge 一致性 | 10% 子样本复判，一致率 ≥ 90%，否则该批 L3 标记为不可用 | 校准分箱复核 |
| 7 | 三臂齐全 | 每 query × 每臂 × 每 sample 的记录都存在，无静默丢弃 | 五组齐全 pass |
| 8 | CI 与标志自洽 | CI 用未舍入百分位；支持标志由原始值判定；反判一次确认无矛盾 | `comparisonFlags` |

检查项数目标：**≥ 60 项**（8 类 × 每类细项）。落地时按 KT 的
`auditGraphDktResults` 结构写，输出 `checks[]` + `passed/failed` 汇总 + 全文哈希。

## 8. 判定矩阵

三个量：`ΔREL = R − X`（净检索增益）、`ΔRET = R − N`（总增益）、`coverage`（§5.2）。

| ΔREL | ΔRET | coverage | 判定 | 下一步 |
|---|---|---|---|---|
| 显著正 | 显著正 | ≥ 0.8 | **build** | 收益真实，可以进产品/扩展规模 |
| ≈ 0 | 显著正 | 高 | **fix-generator** | 增益来自"有上下文"，检索无用；先看 O 臂确认模型是否真在用上下文 |
| ≈ 0 | ≈ 0 | 高 | **stop** | 模型本来就会；这个任务做 RAG 没有意义，换任务 |
| 负或 ≈0 | 负或 ≈0 | < 0.6 | **fix-corpus** | 语料缺答案，调模型是浪费时间 |
| ΔREL 显著负 | — | — | **作废** | 检索在伤害效果，先查分块与 prompt 冲突 |
| X 臂长度不匹配 / 泄漏断言失败 | — | — | **作废重跑** | 违反协议，结果不可用 |

阈值（"显著"）在 Stage 0 由噪声底 σ 推出，例如 `|Δ| ≥ 2σ 且 bootstrap CI 不跨零`。

## 9. 复用映射（哪些能直接搬，哪些必须重写）

| 现有文件 / 函数 | 能否复用 | 说明 |
|---|---|---|
| `bootstrapStats.js` → `mulberry32` `percentile` `ciPreciseOf` `pValueOf` | **直接 require，零改动** | 纯函数，与 KT 语义无关；未舍入 CI 判向的纪律原样保留 |
| `bootstrapStats.js` → `buildStudentSampler` | **零改动复用** | 它只按 `rows[i].userId` 分组重采样；适配层把 `queryId` 写进 `userId` 字段即可，逻辑完全同构 |
| `bootstrapStats.js` → `buildEvaluator` | **不可复用** | AUC/LogLoss/Brier 是二分类概率口径，RAG 不是。需新写 `meanScoreEvaluator`（约 30 行：重采样权重下的加权均值） |
| `bootstrapStats.js` → `bootstrapAllModels` | **需参数化（约 40 行）** | 它内部写死 `buildEvaluator`；抽出 `evaluator` 参数即可同时服务 KT 与 RAG |
| `priorSignalProbe.js` → `groupKFold` | **改 key 复用** | `userIds` 换成 `queryClusterIds` / `docClusterIds`，洗牌+取模逻辑不动 |
| `graphDktExperiment.js` → 指纹 / 纳入 pass / `restat` / `--reason` 留痕 | **结构照搬，代码重写** | `restat` 在 RAG 里价值更大：重跑生成很贵、重算指标很便宜，改判分口径不应重跑 LLM |
| `auditGraphDktResults.js` → 检查项组织 + 哈希绑定 | **结构照搬** | 检查内容全换，骨架（`checks[]` / 汇总 / 源码哈希）保留 |
| `aggregateGraphDktSeeds.js` → 四道闸门 + 从原始记录重算 | **结构照搬** | "聚合器不接受被审计后修改的成绩"这条纪律原样适用 |

诚实结论：**能零改动搬的只有约 120 行的统计工具，其余是结构与纪律的复用，不是代码复用。**
这部分恰恰是最有价值的——纪律比代码贵。

## 10. 分期落地

| 阶段 | 产出 | 门槛 |
|---|---|---|
| **P0** | 语料清单 + 分块 + doc 簇 + `answer_in_corpus_rate` + query 簇 | 覆盖率达标才继续 |
| **P1** | `rag-eval-config.json` 冻结 + 三臂冒烟（20 条） | 预算等长断言通过 |
| **P2** | Stage 0 噪声底 pilot（dev 上，3 次重复） | 得到 σ，写入阈值 |
| **P3** | 三臂（+O）全量运行 | eval 集首次解封 |
| **P4** | 审计器 60+ 项 | 全绿 |
| **P5** | 聚合 + 判定矩阵 + 一页决策备忘 | 判定落定 |

P0 的产物在工程上也是有用的（覆盖率报告能直接告诉你语料该补什么），
即使最终判定是 stop，P0 也不算白做——这一点和 KT 不同，KT 的覆盖率结论是一次性的。

## 11. 必须新增、KT 里没有的纪律

1. **生成采样次数进配置**（`samplesPerQuery`），且聚合规则预注册（均值 or 多数投票）。
   中途改聚合方式 = 换指标，必须重算全部历史（走 `restat` 留痕）。
2. **judge 版本等同尺子**：judge 换模型/换 prompt，全量 L3 作废重算，不能新旧混算。
3. **L1 检索指标必须报**，即使不做决策。它是唯一零噪声的层，用来判断"是检索没找到"
   还是"找到了但没用上"——没有它，所有失败都长一个样。
4. **拒答率单独报**。RAG 系统的失败常表现为"资料中未提及"，这个比例三臂间若差异大，
   说明 prompt 或分块有问题，会污染主指标。
